# AGENTS.md — golfgame

Server-authoritative top-down **minigolf with fading gravity** on SpacetimeDB —
sibling of `~/spacegame`, same tech stack, same conventions. Each player has
their own ball on a shared course (no ball-ball collisions). Planets are solid
circles that the ball bounces off AND that pull the ball with inverse-square
gravity — except the pull **fades to zero** during each shot (see "Mechanic").

## Running things

`export PATH="$HOME/.local/bin:$PATH"` first.

The dev DB is **shared with spacegame**: it's the single in-memory instance on
`127.0.0.1:3000` (data dir `/tmp/stdev-data`) hosting both the `spacegame` and
the `golfgame` databases. Check it's alive with `ps aux | grep standalone`.
Start it like:
`spacetime start --in-memory --listen-addr 127.0.0.1:3000 --data-dir /tmp/stdev-data &`

```bash
# Build module fast (iteration) / CLI does a release build for publish
spacetime build --debug

# Publish to DEV (fresh schema? add --delete-data=always — wipes the golfgame db only)
spacetime publish --server local --yes
#   ("local" nickname = 127.0.0.1:3000; see `spacetime server list`)

# Headless tests (dev DB must be running):
cd client && npm run test:smoke      # lobby→vote→start→corridor check→MIRROR TEST→putt out
                                     # →advance+reset→retee→to_lobby→10-player cap
cd client && npm run test:rejoin     # token persistence → same identity + ball after reload
npx tsc --noEmit                     # type-check (vite dev doesn't fail on TS errors)

# Client dev server
cd client && npm run dev             # http://localhost:5173
```

## Full change workflow (do all of it, in order)

1. Edit `spacetimedb/src/lib.rs` (and mirror physics into `client/src/world.ts` — see invariant below).
2. `spacetime build --debug` until green.
3. Publish to dev (`--server local`, add `--delete-data=always` after schema changes), run `test:smoke` + `test:rejoin`.
   **smoke.ts contains the mirror test**: it runs the identical shot through
   `world.ts simulateShot` and requires the client rest position to match the
   server's within 0.01 px (it currently matches to the bit, Δ=0.00e+0).
   If it drifts, the mirror broke — fix before anything else.
4. If the module **schema** changed (tables/columns/attributes): `spacetime generate --lang typescript --out-dir client/src/module_bindings` (run from project root). In non-interactive mode it does NOT delete orphan files — delete stale `*_table.ts` / `*_reducer.ts` manually.
5. Client changes: `cd client && npx tsc --noEmit`.
6. (Only when a live instance exists) hot-swap + redeploy the client bundle.

## THE invariant (most important thing in this repo)

**`client/src/world.ts` must reproduce the server op-for-op: physics AND
course generation.** The client predicts its own ball locally at 60 fps (exact
substeps of `SUB_DT = 0.05/8`), draws the aim trajectory with the same code,
and generates the identical course from `(seed, hole_idx)` that the server uses:

- Same constants, same **order of operations** (gravity → friction → integrate;
  then boundary → planets → hole check → settle check).
- Use plain `sqrt` everywhere — **never `hypot`** (Rust `hypot` and JS
  `Math.hypot` can differ in the last ulp, which flips boolean checks like the
  hole capture).
- f64 on both sides; both must be semi-implicit-ish Euler in the same sequence.
- The course is GENERATED: `generate_hole(seed, hole_idx)` in lib.rs mirrors
  `generateHole(seed, holeIdx)` in world.ts. The RNG stream is a contract:
  same counter-based `gen(seed, n)` (murmur3 `fmix` finalizers over 32-bit
  words — JS uses `Math.imul`/`|0`/`>>> 0`), same draw order (flip, tee,
  cup, optional redraws, planet count, then per-planet x/y/r in a 40-try
  rejection loop), same acceptance predicates. Reorder ONE draw and every
  subsequent planet changes.
- If you add a physics effect on one side, add it to the other in the same tick.

Reconciliation behavior (main.ts): own ball lerp 50% toward each server row,
hard-snap when >40 px; the authoritative `shotAge` (drives the gravity fade)
lerps 50% too, snap guard 0.1 s. Other players' balls render with 100 ms
interpolated snapshots. Don't "improve" these numbers without playtesting.

## The mechanic (don't "fix" it without asking)

Fading gravity, exactly as specified by the player:

1. **Estimate at shot time, as if gravity didn't exist.** Constant rolling
   friction `FRICTION = 120 px/s²` decelerates the ball from `v0`; it would
   stop after `t_stop = v0/FRICTION` having travelled `D = v0²/(2·FRICTION)`.
2. `t_half` = the time that gravity-free ball needs to cover **half of D**:
   closed form `t_half = (v0/FRICTION)·(1 − √2/2)` (≈ 0.293·v0/FRICTION).
   Walls/planets/gravity are deliberately NOT in the estimate — it's naive by
   design (a pull can re-accelerate the ball, so real shots can outlive it).
3. `gmult(t) = max(0, 1 − t/t_half)`: planets pull at 100% the instant of
   impact, falling linearly to 0% at `t_half`. After that the ball coasts on
   friction alone and settles — gravity never hinders the stop.
4. `t_half` is frozen into the player row at shot time (`shot_age`/`tHalf`);
   the clock always runs from the moment of impact.

Tuning intent:

- `FRICTION = 120`: full-power shot (700 px/s) stops in ~5.8 s / ~2041 px.
- `G_GOLF = 3000` (tuned 2026-09-27: 500 was a visual non-effect — drives
  bent ~30 px; at 3000 they bend ~170 px and the peak pull reaches ~4×
  friction), planet `mass ∝ r²`: a 700 px/s ball grazing a 50 px planet at
  100 px gets pulled hard early in the shot; near `t_half` the same flyby does
  almost nothing.
- `REST = 0.86` wall & planet bounce.
- `CAPTURE_SPEED = 100`: fast balls roll **over** the cup (real golf).
- **Settle only when `gmult == 0` AND speed < `SETTLE_EPS = 2 px/s`** — while
  the fade is active a planet may still pull a slow ball back, and the ball
  must not freeze mid-pull. (With the gmult guard this can't jitter: no
  acceleration once the fade completes.)
- Ball state machine: `0 READY → 1 ROLLING → 0 READY` (settle) or
  `2 HOLED` (waits for the hole advance). `hit` is rejected while rolling.
- A shot that crosses the cup at < CAPTURE_SPEED is captured on the first
  substep inside the 15 px radius — a ball can never settle inside the radius
  without dropping. If a test ever sees "at rest inside the cup radius",
  suspect a stale target (client aiming at an old hole's cup after an advance),
  not the engine.

## Course (procedural, guaranteed path)

1600×900 world. Per `(seed, hole_idx)` the generator draws (in this exact
order — see invariant): a side-flip, tee in one x-box, cup in the other
(redrawn up to 24× until tee–cup ≥ 700 px), then 4–6 planets. A planet is
accepted only if it keeps: 50 px world margin, **corridor clearance ≥
r + 85 px from the straight tee→cup segment** (the guaranteed straight line
no planet blocks), ≥ r+90 from the tee, ≥ r+100 from the cup, and
≥ r+r′+80 from every other planet. No internal walls.

Guarantee: a full-power straight drive tee→cup never hits a planet
(`straightDrivePower(d) = sqrt(2·FRICTION·d)` ≤ MAX_SHOT for the worst-case
distance). It does NOT guarantee the ball stops at the cup — planet gravity
bends the path, so drives routinely stop ~20–40 px short of the cup line;
that's normal, the putt finishes it. Par per hole: 3 if tee–cup < 1000 px
else 4.

Retuning the generator = editing the draw order/predicates in BOTH files;
the smoke-test mirror check (Δ < 0.01 px, currently bit-exact) re-validates
the physics on whatever course the live seed produced.

## SpacetimeDB v2 gotchas (learned in spacegame — full API in `spacetimedb/sdk-reference.md`)

- **A panic in the tick reducer kills the heartbeat silently.** Use flags + a
  single update path; never `update` a row you just `deleted`.
- `.pk().update(row)` takes a **full row** — `..p.clone()` (struct update needs
  the old value cloned; non-Copy String fields).
- Reducers take **object params** from the client: `db.reducers.hit({ dx, dy, power })`;
  zero-arg reducers still take an object: `db.reducers.retee({})`.
- `ctx.random()` needs a type annotation; `ctx.connection_id()` returns `Option<ConnectionId>`.
- Heartbeat = scheduled table (`tick_timer`, `ScheduleAt::Interval(50ms)`), started once in `init`.
- **Generated TS bindings are camelCase**: Rust `shot_age` → `row.shotAge`,
  `t_half` → `row.tHalf`. (Bit us in spacegame-adjacent code.)
- Anonymous local connections get a **persistent identity + JWT token** — what
  the rejoin feature stores.

## Round / lobby model

- Tables: `Round` (row id 0: phase 0 lobby / 1 playing / 2 finished, seed,
  holes 8|16, hole_idx) + `Player` (ball fields + `phase`, `hole`, `strokes`,
  `totalStrokes`, `courseChoice`, `connected`, `offline_since_tick`).
- Max 10 players (`spawn` rejects the 11th). Everyone spawns into the LOBBY
  parked at the default tee (140,450) on a 5-wide identity-sorted spread grid
  (14 px spacing → corner slots sit 31.3 px from the tee center; test
  thresholds must allow ≥ 35 px).
- Any player may `startMatch`; length = majority `courseChoice`, tie/solo → 8;
  fresh `seed = ctx.random()`. All players → PLAYING at the generated tee
  (same spread grid). Late joiners stay in the lobby = spectators.
- Hole advances in the tick when **every** PLAYING player is HOLED (re-reads
  the table after the physics pass); on the last hole → FINISHED.
  `toLobby` resets everyone (allowed from playing or finished).
- The advance resets balls to the new tee in the SAME tick it bumps `hole_idx`
  — a client that keeps aiming at the old hole's cup will putt into a ghost
  target ~100+ px away and "settle without capture". Tests must re-read the
  round row after every settle.

## Rejoin / identity model

- Client stores `golfgame.<host>.token|identity|name` in localStorage (per-server-host
  keys — never send one DB's token to another DB).
- Server: a `conn` table tracks live connections; a disconnected ball is marked
  `connected=false` and lingers **30 s** (`GRACE_TICKS`) rendering as a dim ball, then is
  removed (its round is gone). Reconnecting with the same token inside the grace window resumes the exact ball —
  **mid-roll included** (main.ts re-anchors `shotAge`/`tHalf` from the row).
- `client_disconnected` must NOT delete the player (that's what breaks reload-rejoin).
- The tick only updates a player row when something changed (rolling ball, or a
  connection flip) — idle balls are silent. Don't "fix" this back to
  update-every-tick without considering the client traffic.

## Client URL gotcha (inherited from spacegame)

The SDK builds its socket URL via `new URL("v1/database/<name>/subscribe", uri)` —
**without a trailing slash the last path segment of `uri` is replaced by the relative
ref**. So a same-origin proxy prefix only works WITH a trailing slash:
`VITE_WS=wss://host/golfgame-ws/` (correct), `wss://host/golfgame-ws` (broken).

## Misc

- **Client-side `db.db.<table>.id.find()` reads the client's REPLICATED state.**
  A script must call `db.subscriptionBuilder().subscribeToAllTables()` or it
  sees nothing (no initial sync). Bit us while debugging: server state looked
  "deleted" while it was just never replicated to the probe.
- **Row batches:** a capture row and the same-tick-ish advance-reset row can
  arrive in one delivery; last-row pollers can skip the capture row. Wait on
  "a new row since index N" or scan history, never only `rows.at(-1)`.
- Git: local-only repo; the user pushes themselves. Commit small, descriptive
  commits after each verified change.
- The dev DB on :3000 doesn't survive reboots; `npm run test:*` need it running.
- Don't commit `client/.env.local` (gitignored).
- `spacetimedb/target/`, `client/node_modules/`, `dist/` are gitignored build output.
